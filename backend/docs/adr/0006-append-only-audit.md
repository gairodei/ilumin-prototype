# ADR 0006: Server-authoritative, append-only audit

- Status: Accepted for Stage 1A (addresses P10 S-04)

## Decision

- `audit_event` records:
  - the actor (`user` with `actor_user_id`, or `system` with a label), checked by a CHECK constraint;
  - the actor's roles and scope at decision time;
  - the `operation` (`module.verb`) and `outcome` (`succeeded` / `refused`);
  - the entity type and ID;
  - `request_id` and `correlation_id`;
  - `client_ip`;
  - before/after JSON;
  - the reason;
  - metadata;
  - `occurred_at` (server `clock_timestamp()`) and a monotonic `seq`.
- **Server-derived only**:
  - The actor comes from the authenticated principal.
  - The request ID is generated by the server.
  - The IP is the socket address, and `X-Forwarded-For` counts only from proxies listed in `TRUST_PROXY` (tested).
  - Nothing comes from the request body.
- **Append-only enforcement**, two layers:
  1. Privileges: the API role has `SELECT, INSERT` only.
  2. `BEFORE UPDATE OR DELETE` and `BEFORE TRUNCATE` triggers raise for every role, including the owner. Removing them takes a reviewed migration.

  Tests cover both layers, and also cover the API role failing to disable the triggers or drop the table.
- **Same transaction**: `appendAudit(tx, …)` is called with the state change's transaction client, so the audit row commits or rolls back with it (P10 §D). Refusals are written separately.
- `reasonRequired: true` refuses to write an event with a blank reason (used for role grants and revocation, status changes, and overrides).
- The application exposes no audit update or delete endpoint (tested via the route inventory).

## Not in Stage 1A

- Audit read API per role.
- Retention period (client decision D-01).
- Optional hash chain.
- Off-database archive.
